| 方向 | 倍率 | 銘柄 |
|---|---|---|
| ブル | 1倍 | **1321**（NEXT FUNDS 日経225連動型上場投信） |
| ブル | 2倍 | **1570**（NEXT FUNDS 日経平均レバレッジ・インデックス連動型上場投信） |

🔵 4本すべて NEXT FUNDS（野村アセット）で揃えた。値付けと出来高の性質が近く、比較しやすい。

🔴 **同時に持てるのは1銘柄だけ**（ブルとベアの同時保有は相殺するだけで無意味）。
LLM は毎回 **方向（ブル / ベア / なし）× 倍率（1倍 / 2倍）** を選ぶ。
**倍率の選択がそのまま確信度の表現**になる — 確信が高ければ2倍、低ければ1倍。
🔵 これは既存の方針（「ブル/ベア 1倍2倍 ETF（現物）でシグナルを表現」）と一致する。

🔴 **4本にしたことの代償＝検証のサンプルが分散する**。「ブル2倍で勝ったか」を銘柄別に見ると N が小さくなるので、
**Go/No-Go は銘柄別ではなく口座全体の成績で判定する**（§2 論点2）。銘柄別の内訳は参考値として出すに留める。

🔵 価格取得は追加コストゼロ。`fetch-jpx.mjs` が既に使っている
`https://query1.finance.yahoo.com/v8/finance/chart/{code}.T` の経路に4本を足すだけ。

🔴 **LLM 最終判断は、こちらの推奨（決定論が判断／LLM は解釈）とは逆の選択**。
懸念（バックテスト不可・Go/No-Go を数値で決められない）は §1 論点3 に記載したうえで、
**ユーザーの判断として設計に反映した**。以降の設計は「LLM が判断器である」前提で、
その選択の弱点を実務的に埋める形で組んである（§4 の記録・§5 の対照群）。

## 1. 先に結論（3点）

### ① v1 にリアルタイムAPI・ブラウザスクショ・PC常駐は要らない

引け値ベース＋**既に動いている GitHub Actions**（`.github/workflows/fetch-data.yml`／平日 19:30・21:30 JST、土曜 09:00 JST）で完結する。
🔴 **判断そのものは平日 08:30 JST の回で実行する**（2026-08-10 に19:30から移動）。材料は前営業日の終値のままで、
通知を読んでから寄り付きで執行するまでの間隔を縮めるため。
仕様書 §5 の「PCつけっぱなし前提（cron / 証券API常駐 / Claude Code をローカル稼働）」は、v1 では**丸ごと不要**。

### ② TEV をそのまま判断材料の中心に据えてはいけない

`public/data/backtest_results.json` の実測（`logic_version: v2-symmetric-restoring`・52週）:

| | 値 |
|---|---|
| 全体勝率 | **44%** |
| Bull 勝率 | 63% |
| Bear 勝率 | **39%** |
| 確信度 50-59% 帯 | n=33・実勝率 42.4%・**gap −11**（自信過剰） |

🔴 LLM が最終判断するとしても、**渡す材料の中身は変わらず TEV** になる。
この数字を LLM に伝えないまま「TEV を見て判断しろ」と渡すと、**負けている指標を根拠に判断させることになる**。
→ **プロンプトに TEV の実測成績（44%・Bear 39%・自信過剰）を明記して渡す**（§3.3）。
　 20年R&D で検証済みの v5a 系（トレンドフィルター＋押し目）の観測値も併せて渡す。

### ③ LLM 判断はバックテストできない。だから「対照群」を並走させる

同一入力でも出力がぶれるため、過去データで LLM の判断を再現できない。
Go/No-Go（§2 論点2）はフォワードテストでしか測れず、週次シグナルなら 30トレードに**約7ヶ月**かかる。

🔴 **対策＝決定論ルールを「対照群」として同じ期間・同じデータで疑似記録だけする**（§5）。
これで「LLM は決定論ルールより上手いのか」が実測できる。
LLM 判断を否定せず、**評価可能にする**ための唯一の実務的な手段。

## 2. §10「必ず回答・確認させる論点」への回答

### 論点1 — リアルタイム要件は本当に要るか → **v1 では不要**

**省ける理由**
1. スイング（数日〜数週間）の建玉に、ザラ場の秒単位の値は効かない。エントリーが数十円ずれても、
   数百〜数千円幅を狙う建玉の損益への寄与は小さい。
2. 🔴 **既存のバックテスト資産はすべて日次終値ベース**（`backtest-tev.mjs` は週次 close、
   `backtest-system-v*.mjs` は日次）。リアルタイムで判断すると**検証した条件と執行の条件が食い違う**。
3. kabuステーションAPI は PC常駐＋セッション維持＋再接続処理が要り、**最も壊れやすい部分**。
   ここを v1 に入れると、エッジの検証ではなく配管の保守が仕事になる。
4. 🔴 **LLM 判断ではコストが回数に比例する**（§7）。1日4回は判断材料が同じまま費用が4倍になる。

**採用してよくなる条件（v2 で入れる）**
- v1 の記録で「引け判断 → 翌営業日寄付き執行」の滑りが期待値を有意に食い潰していると**数値で出たとき**
- 損切りをザラ場中に執行しないと許容できない、と実測で分かったとき

**判断回数**: v1 は **引け後1回**（日次終値確定後）。仕様書 §0 の「1日4回」は v1 では 1回に落とす。
判断材料（JPX 需給データ）は**日次更新**なので、4回聞いても**同じ入力で4回聞くだけ**になる。

---

### 論点2 — Go/No-Go 基準を着手前に数値で固定

提案（🔴 最終決定はユーザー）:

| | 基準 |
|---|---|
| 判定単位 | **クローズしたトレード数 N ≧ 30** |
| **Go** | 期待値 > 0 ／ **期待値が対照群以上** ／ **最大DD が対照群より浅い（同等まで可）** |
| **No-Go（中止）** | N=30 時点で 期待値 ≦ 0、または**対照群に明確に負けている**（期待値もDDも下） |
| 早期打ち切り | N=15 時点で期待値が大きく負 |

🔴 **DD 条件は絶対値ではなく「対照群比」にする**（2026-08-09 修正）。
第2版では DD ≧ −20% としていたが、**対照群の実測が −42.68%**（§5）だったため、
絶対値の基準は AI に対照群より狭い土俵を強いることになり、
「**AI に裁量を持たせて判断させる**」というユーザーの方針（2026-08-09）と噛み合わない。

🔴 **「対照群を上回っている」を Go 条件の中心に据える**。
LLM 判断はバックテストできないので、「過去に効いたか」ではなく「**同時点で決定論ルールより上手いか**」で測る。
これなら実時間の並走だけで判定できる。

🔵 **評価は期待値とDDの両面で見る**。§5 の実測で「持ちっぱなしのほうが CAGR は上、違いは DD」と分かったため、
リターンだけを見ると対照群の価値（DD半減）を見落とす。

🔴 仕様書の「数週間」は楽観的。**約7ヶ月**を見込む（§1 ③）。

### 論点3 — LLM の役割 → 🔴 **ユーザー決定＝LLM が最終判断**

**ユーザーの選択（2026-08-09）**:
> 疑似トレードとしてLLMが最終判断です。私はそれを参考にリアルトレードでも同様のトレードをします。（それは私の判断です）

**こちらが述べた懸念（記録として残す）**
1. LLM は同一入力でも出力がぶれる → **バックテストできない**。Go/No-Go を過去データで前倒しできない。
2. 既存資産（`tevCore.mjs`・`backtest-*.mjs`・キャリブレーション）はすべて決定論側にある。
3. 判断器が変わるとゼロから測り直しになる（モデル更新・プロンプト変更のたび）。

**ユーザー判断を受けての設計**（懸念を実務的に埋める4点）

| # | 対策 | 目的 |
|---|---|---|
| 1 | **判断の入出力を丸ごと git に保存**（プロンプト・データ・生レスポンス・モデルID・effort） | 再現できない代わりに**証拠を残す**。後から「なぜこの判断をしたか」を追える |
| 2 | **モデルIDと effort を固定して記録**（`claude-opus-5` / `effort` 値） | モデルが変わったら**別の判断器**。同じ成績表に混ぜない |
| 3 | **出力を Structured Outputs で固定**（`output_config.format` の json_schema） | 「売り/買い/待機・数量・確信度・理由」を毎回同じ形で受け取る。パース失敗もぶれもなくす |
| 4 | 🔴 **決定論ベースラインを対照群として並走**（§5） | LLM が決定論より上手いかを実測。バックテスト不可を実時間で埋める |

🔴 **損切りだけは決定論のまま**。これは仕様書 §3・設計原則3（「損切りラインは事前に数値で固定し、AIに都度判断させない」）
と一致しており、LLM 最終判断とも矛盾しない。**LLM は建てるかどうかを決め、損切り値は番人（純関数）が決める。**

## 3. 全体アーキテクチャ

### 現状のパイプライン
```
GitHub Actions (fetch-data.yml)
  → scripts/fetch-jpx.mjs → public/data/*.json → commit → Vercel 自動デプロイ → フロントが読む
```

### 追加する経路
```
GitHub Actions (fetch-data.yml の後段に1ステップ足すだけ)
  → scripts/robo-trade.mjs
      0. Chatwork から実保有キャプチャを取得 → vision で読取 → real_position.json  ← ★ 実情の取り込み
      1. public/data/*.json を読む（直前のステップで更新済み）
      2. robotStrategy.mjs（決定論・対照群）でシグナルを算出       ← 記録のみ
      3. Claude API に判断させる（本番判断）                      ← ★ LLM が最終判断
         入力＝ロボ口座（自分の建玉）＋実保有（ユーザーの現状）＋需給＋価格＋イベント
      4. 損切り値を決定論の純関数で確定                            ← LLM には決めさせない
      5. public/data/robo_account.json を更新（約定を追記・建玉を再計算）
      6. 判断ログ（入出力の全文）を public/data/robo_logs/{date}.json に保存
      7. Chatwork へ通知（本人のルーム）。🔴 hold の日も毎日送る
  → 既存の commit ステップに相乗り → Vercel 自動デプロイ
  → フロント「エンジン」タブが robo_account.json を読んで表示（管理者のみ）
```

### 🔵 なぜ Firestore ではなく `public/data` の JSON か

仕様書 §3 は「localStorage ＋ Firestore（ログイン時同期）」としているが、**ロボ口座は提案を変えたい**。

| | 理由 |
|---|---|
| ロボ口座は**1つの口座** | ユーザー個別データではない。書き込み主体はサーバー（Actions） |
| 🔴 **履歴が git に残る** | 改竄の余地がなく「あの時どう判断したか」を後から追える |
| 🔴 **LLM 判断では決定的に効く** | 再現できない判断器なので、**残っている記録だけが証拠**。git の追記履歴がそのまま監査ログになる |
| 既存パイプラインに乗る | fetch → commit → deploy の流れをそのまま使える |

🔴 ユーザー個人のメモ（旧ポジション分析レポート）は従来どおり localStorage + Firestore に残す。

## 3.3 LLM 判断の設計（本設計の中心）

### 使う API とモデル

- **Anthropic TypeScript SDK**（`@anthropic-ai/sdk`）。実行は Node ESM（`scripts/robo-trade.mjs`）。
- **モデル: `claude-opus-5`**（$5 / $25 per MTok）。
- **Adaptive thinking がデフォルトで有効**。`output_config: { effort: ... }` で深さを制御する。
- 🔴 **`temperature` / `top_p` / `top_k` は使えない**（Opus 5 では 400 エラー）。
  ＝ **「毎回同じ判断にするために temperature=0」という手は使えない**。ぶれは前提。
- 🔴 **`stop_reason: "refusal"` を必ず先に確認してから `content` を読む**（Opus 5 は安全分類器で拒否しうる）。
  拒否されたら**その日は「待機」として記録**し、Chatwork に「判断が取得できなかった」と通知する
  （勝手に決定論の結果で埋めない。判断器が違うものを同じ成績表に混ぜないため）。

### 出力を Structured Outputs で固定する

```jsonc
// output_config.format の json_schema（案）
{
  "type": "object",
  "properties": {
    "action":       { "type": "string", "enum": ["open", "close", "hold"] },
    "symbol":       { "type": "string", "enum": ["1321", "1570", "1571", "1357", "none"] },
    "qty":          { "type": "integer" },
    "confidence_pct": { "type": "integer" },
    "reason":       { "type": "string" },   // 日本語1〜2行。Chatwork の「理由」欄に出す
    "counter":      { "type": "string" }    // 🔴 この判断が外れる条件（反証）
  },
  "required": ["action", "symbol", "qty", "confidence_pct", "reason", "counter"],
  "additionalProperties": false
}
```

- 🔴 **`counter`（反証）を必須にする**のが要点。「この判断が外れるのはどういうときか」を毎回書かせ、
  記録に残す。後から「ロボは自分の負け筋を言い当てられていたか」を検証できる。
- 🔴 **`symbol` の選択がそのまま方向と倍率の意思表示**になる（§0.1）。`hold` のときは `"none"` / `qty: 0`。
- `qty` は LLM が出すが、**資金管理の上限で機械的にクリップする**（LLM に上限を破らせない）。
- 🔴 **建玉があるときに別方向の `open` が来たら、機械的に「決済 → 新規」の2約定に分解する**
  （ドテン。LLM に2ステップ書かせず、コード側で保証する。同時保有を構造的に起こさせない）。
- 損切り値は**スキーマに入れない**。LLM には決めさせず、決定論の純関数が付ける（§6）。

### プロンプトに必ず入れるもの

1. **現在のロボ口座状態**（建玉・平均取得単価・評価損益・現在の損切り値）
2. **需給データ**（既存 `buildExportJson` の直近12週 JSON）
3. **価格データ**（対象ETFと日経225の日次 OHLC・MA・ATR）
4. **今後5営業日のイベント**（既存 `buildUpcomingEventsText`）
5. 🔴 **TEV の実測成績**（52週で全体44%・Bear 39%・確信度は自信過剰 gap −11）
   ＝ **「この指標はこの程度しか当たっていない」と明示して渡す**。伏せて渡すと、
   　 負けている指標を根拠に自信を持って判断される。
6. 🔴 **20年R&D の結論**（トレンドフィルター必須／逆張りは確定下落局面でのみ／
   CAGR と DD は両立に限界があり現実解は CAGR 15〜20% × DD −40% 圏）
7. **決定論ルール（対照群）の今日のシグナル**
   🔴 ただし「これに従え」とは書かない。**参考値として見せ、違う判断をしたなら理由に書かせる**。
8. **売買推奨ではなく疑似口座の操作である**という位置づけ（本人専用・状態記述の方針は維持）

### 🔴 営業日カレンダー（2026-08-09 追加・ユーザー指示）

> 「トレード時間は、ぽいロボカレンダーの営業時間みてね」「あと、トレードはカレンダーとかも見てね」

**① 休場日は走らせない。**
`scripts/robo-trade.mjs` は最初に `marketStatus(todayJst())` を見て、東証が休場なら
**判断も口座更新も通知もせずに終了する**。

- なぜ止めるのか＝休場日に「本日は hold」と通知すると、**判断した日と何もしなかった日が
  区別できなくなる**。成績の分母（判断回数）が水増しされ、対照群との比較が壊れる。
- 判定は `src/utils/marketCalendar.mjs`。**アプリのカレンダー表示と同じ実装**を使う
  （`marketHolidays.ts` はこの .mjs を re-export するだけの入口に変えた）。
  🔴 休場条件を二箇所に書くと、片方だけ直して祝日に発注する事故になる。
  `tevCore.mjs` / `robotStrategy.mjs` と同じ「単一情報源」扱い。
- 日付は **JST で判定する**（Actions は UTC で走るため `Intl` で Asia/Tokyo に寄せる）。
- 配線確認用に `--force` で休場日でも走らせられる。**本番では付けない**。

**② イベントをプロンプトに渡す。**
`upcomingEventsText()` が **今後5営業日** の FOMC・日銀・CPI・PCE・雇用統計・短観・介入実績を
1つの節にまとめてプロンプトへ入れる（上の「プロンプトに必ず入れるもの」4番の実装）。

- 出どころは `src/utils/macroCalendar.ts`＝**アプリのカレンダーと同じ表**。
  Node の型ストリップ（Node 22.18+ / 23.6+ で既定）で `.ts` を直接 import している。
  → カレンダーの年次更新（`docs/maintenance/calendar-dates-check.md`）が
  　 そのままトレード側にも効く。二重管理しない。
- 🔴 **読めなくても判断は続ける**（警告を1行足すだけ）。イベントは「あれば効く」情報であって、
  これが無いと判断できないものではない。型ストリップが使えない環境で全停止する方が損。

### プロンプトキャッシュは効かない（明記）

🔴 **1日1回の実行では prompt caching は無意味**。キャッシュの TTL は 5分（既定）または 1時間で、
実行間隔が24時間なので毎回ミスする。キャッシュ用の breakpoint を置いても**書き込み料（1.25倍）を払うだけ**。
→ **v1 では `cache_control` を使わない**。1日4回に増やしても間隔が数時間なので同じ（1時間TTLでも足りない）。

### effort の初期値

- **`effort: "high"`（既定）から始める**。判断の質が価格に直結するため、ここは削らない。
- コストが問題になったら `medium` を試す（§7 の見積もり参照）。
- 🔴 **effort を変えたら判断器が変わったものとして扱う**。`robo_account.json` の `logic_version` を上げ、
  成績表を分けて集計する。

## 5. 🔴 決定論ベースライン（対照群）— LLM 判断を評価可能にする仕掛け

**やること**: 毎回 LLM に判断させるのと同時に、`robotStrategy.mjs`（決定論・v5a 系）でも
同じデータからシグナルを出し、**別の疑似口座として記録だけする**（通知はしない・執行もしない）。

**測れるようになるもの**

| 指標 | 意味 |
|---|---|
| LLM の期待値 − 決定論の期待値 | **LLM を使う価値があるか**（これが本丸） |
| 一致率（`agreement_pct`） | LLM が決定論と違う判断をした割合。低ければ「LLM 独自の読み」が多い |
| 不一致時の勝敗 | 🔴 **LLM が決定論に逆らったとき、勝っているか負けているか**。ここが最も情報量が多い |

🔵 **決定論側は過去データでバックテストできる**ので、対照群の期待成績は着手前に分かる。
＝ LLM のフォワードテストの結果を「決定論の既知の成績」と比べられる。

### ✅ 対照群の実測（2026-08-09・`scripts/backtest-robo.mjs`）

判断=終値／約定=翌営業日始値／コスト片道0.04%／元本100万円。

| | トレード | 勝率 | 期待値 | CAGR | 最大DD | 損切後逆行 |
|---|---:|---:|---:|---:|---:|---:|
| **A) 指数近似（^N225×2倍・20年）** | 93件 | 34% | +54,317円 | 9.23% | **−42.09%** | 13回 |
| 参考: 日経2倍を持ちっぱなし | 7件 | 14% | +811,243円 | **9.89%** | **−88.42%** | 3回 |
| **B) ETF実データ（1570/1357・2014-07〜）** | 57件 | 40% | +47,347円 | **11.39%** | −42.68% | 10回 |
| 同期間の指数近似 | 59件 | 36% | +40,989円 | 10.65% | −41.96% | 10回 |

🔴 **Go/No-Go の比較対象は B)（ETF実データ）を使う。**

**この実測から分かった、設計に効く3点**

1. 🔴 **対照群の価値はリターンではなくドローダウンにある。**
   20年の指数近似で、日経2倍を**持ちっぱなしのほうが CAGR は上**（9.89% vs 9.23%）。
   違うのは DD で、**−88% を −42% に半減させている**のが対照群の仕事。
   ＝ **LLM の評価軸も「儲けたか」ではなく「同じ儲けをどれだけ浅い谷で取ったか」**にする。
   既存の20年R&Dの結論（CAGR と DD は両立に限界があり、現実解は CAGR 15〜20% × DD −40% 圏）とも一致。

2. 🔴 **勝率は 34〜40% しかない。それでも期待値はプラス。**
   勝ちが大きく負けが小さいトレンドフォロー型の典型。
   ＝ **プロンプトで「勝率を上げろ」と指示してはいけない**。勝率を上げにいくと利を伸ばせず期待値が壊れる。
   プロンプトには「**勝率は低くてよい。負けを小さく、勝ちを伸ばす**」と明示する。

3. 🔴 **ベアは20年で63日（全体の1%）しか立たない。**
   ベア用に2銘柄（1571 / 1357）を用意したが、**決定論の対照群ではほぼ使われない**。
   ＝ ベア側は検証サンプルが決定的に足りず、対照群としての比較力を持たない。
   🔵 逆に言えば**ここが LLM の差別化ポイント**になりうる（決定論が撃てない場面でベアを使えるか）。
   ただし**ベアの成績だけは対照群と比較できない**ので、Go/No-Go は口座全体で判定する（§0.1 と同じ理由）。

🔵 **補足**: ETF実データ（B）は指数近似より **CAGR +0.74ポイント良かった**。
レバETFの減価で悪化するという事前の懸念は、**この期間（2014-07以降のトレンド相場）では起きなかった**
— 減価より複利が勝ったため。🔴 ただし横ばい相場では逆に出るので、近似は今後も参考値に留める。

**内訳**: ブル 2239日（45%）／ベア 63日（1%）／ノーポジ 2631日（**53%**）。
🔵 **半分以上は何も持たない**のが対照群の姿。LLM にも「持たない日があってよい」と伝える。

🔴 **これは「LLM をやめて決定論にする」提案ではない**。LLM が本番判断のままで、
その良し悪しを測るための計器を1つ増やすだけ。追加コストはゼロ（API 呼び出しは増えない）。

## 6. 損切りルール（LLM に決めさせない部分）

```
stop = entry − k × ATR20        （ブル建玉。ベアは符号反転）
k = VIX < 20 → 2.0 ／ 20–30 → 2.5 ／ 30 以上 → 3.0
```

- ATR20 は日次 OHLC から算出（`^N225` と対象ETFの日次データ）。
- 🔴 **AI に都度判断させない**（設計原則3・仕様書 §3 と一致）。`robotStrategy.mjs` の**純関数**として実装しテストを書く。
- 🔵 **固定% にしない**理由 = 損切り貧乏の回避。ボラの外側に置く。
- `stop_price` は**建てた瞬間に確定して記録**する。後から動かした形跡が git diff に残る＝**事後正当化を防ぐ**。
- `stop_then_reversed`（損切り後 N 日以内に元の方向へ X% 動いた回数）を記録し、**k が小さすぎないかを検証**。
  N・X の定義は実装時に固定し、後から動かさない。

## 5.4 判断は 15:00・執行は引成（2026-08-11 変更）

🔴 **日経のリターンはオーバーナイト（引け→寄り）に集中している**（26年・1倍）。

| 持ち方 | CAGR | 最大DD | 26年で |
|---|---|---|---|
| オーバーナイト（引け→寄り） | **+11.07%** | −32.6% | **15.30倍** |
| 日中（寄り→引け） | **−4.90%** | −82.6% | **0.27倍** |
| 買い持ち（引け→引け） | +5.62% | −61.4% | 4.14倍 |

日中は方向のないノイズにリスクだけ晒す時間帯だった。前夜S&P500 → 翌日の**寄り**の一致率 74.7% に対し、
**寄り→引けは 49.8%＝コインの裏表**。情報は夜のうちに米国で織り込まれ、寄り付きで反映されて終わる。

🔴 それまでの「08:30 判断 → 翌日の寄りで執行」は、**建てる初日のオーバーナイトを丸ごと逃していた**。

| | CAGR | 最大DD | 売買回数 |
|---|---|---|---|
| 旧: 前日終値で判断 → 翌日の寄りで執行 | +8.00% | −40.9% | 174 |
| **新: 15:00 判断 → 当日の引成で執行** | **+10.33%** | **−37.0%** | 174 |

売買回数は同じで、リターンが上がり DD も浅くなる。

🔴 **先読みではない**ことは実測済み＝15:00 時点の判定と終値での判定は **729日中728日で一致（99.9%）**。
ドンチャン50/25も25日線乖離も動きが遅く、最後の30分で判定が変わることがほぼない。

### 運用の約束

- 判断・通知は**平日 15:00 JST**（`fetch-data.yml` の `cron: '0 6 * * 1-5'`）。
- 🔴 **15:25 までに引成（MOC）で発注する。** ここが守られないと、記録（終値で約定）と実物がずれる。
- 約定は**判断した日の終値**。終値は 15:30 まで確定しないので、判断した日は `account.pending` に積むだけにして、
  次の実行で確定した終値を引いて記録する（§5.5 の仕組みをそのまま使う）。
- 🔴 約定価格は**位置ではなく日付で引き当てる**（`fillPriceOf(symbol, decided_on)`）。
  15:00 実行だと日足の最終行が「今日の途中経過」のことも「前営業日の確定足」のこともあり、
  末尾から数えると休場や取得タイミングで簡単にずれる。
- その日付の足がまだ取れていなければ**約定させずに持ち越す**（`pending-wait`）。

### 採らなかった案

- **後場に建てるが判断は前日のまま**（前日終値で判断 → 当日の引けで執行）→ CAGR **+5.95%** で現行より **−2.05%**。
  オーバーナイトを1回多く取る利益より、**判断が1日古くなる損のほうが大きい**。
- **毎日オーバーナイトだけ持つ**（毎日引けで買い、寄りで売る）→ 理屈は最良だが 26年で6,000回超の売買。
  往復コスト 0.08% に対し1回平均 6.1bp なので**コストで消える**。

## 5.5 約定は「実際の寄値」で記録する（2026-08-11 追加）

🔴 **これまでの割り引き**＝判断は 08:30 に前営業日の**終値**を見て下すが、実際に買えるのは 09:00 の**寄値**。
それまでは終値で約定したことにしていた。実測（1570・直近1年 n=241）で前日終値→寄値の窓は

| | 値 |
|---|---|
| 平均（絶対値） | **2.08%** |
| 中央値 | 1.47% |
| 上位10% | **4.82%** |

平均2%は割り切れる大きさではなく、**測っているものが実物と別**になっていた。

### 直し方＝保留注文（1日遅れて確定）

```
D日 08:30  判断する → account.pending に積むだけ（約定は書かない）
D日 09:00  実際の寄り付き（ユーザーが執行）
D+1 08:30  日足の最終行が D日になっていて、その行の始値＝実際に買えた値段 → その値段で約定
```

- 🔵 バックテストではなく**実運用の記録**なので、1日遅れて確定するだけで精度は本物になる。
- 損切りも同じ。終値で触れたら**判定するだけ**（`detectStopHit`）で、決済は翌朝の寄値。
  窓で飛べばもっと悪い値段になるが、それが実際に降りられる値段。
- 通知には「翌営業日の寄りで執行予定」を出す（書かないと注文したのに口座が変わらないと読める）。

### 窓ガード

🔴 新規建ての注文で、**寄値が既に「判断時点の終値から引いた損切り値」の向こう側**なら建てない。
判断の前提が寄り付きで壊れているので、入った瞬間に損切りという形になるだけ。見送って翌日また判断する。
🔵 損切り値は**判断時点の終値から**引く。寄値から引き直すと、どんなに飛んでいても必ず内側に収まり、ガードが働かない。

### 効きの実例（通し確認）

| | 旧（終値で約定） | 新（寄値で約定） |
|---|---|---|
| 建値 | 30,000（前日終値） | **30,800**（実際の寄値） |
| 手仕舞い | 31,000（損切り日の終値） | **29,500**（翌朝の寄値・窓で飛んだ） |
| 損益 | **+20,000円（勝ち）** | **−26,000円（負け）** |

🔴 同じ値動きで**勝ち負けが逆に出ていた**。窓を無視するとはこういうこと。

### 検討して採らなかった案

- **9:30 に執行する**（ユーザー案）→ 🔴 窓は 09:00 で確定済みなので**取り戻せない**。
  実測では寄値→9:30 の変化は平均 −0.15%（方向の偏りなし）で、**絶対値で平均1.47%のブレが上乗せ**されるだけ（n=14）。
  加えて日足には 9:30 の値が無く、5分足という別経路への依存が増える。
- **執行時刻をユーザーの裁量にする**→ 🔴 疑似口座がその値段を再現できず、さらに
  **AIの成績と人の執行の腕前が混ざる**。同期と YOUR CALL を分けている意味が崩れる。
  → 記録は寄値で固定し、実際の執行時刻とのズレは `divergences` / YOUR CALL 側で測る。

### 6.0 価格の構造を見る（2026-08-11 追加）

```
atrStop = entry − k × ATR20
k = VIX 由来（上表）× イベントが2営業日内なら 1.2
① 直近25本のスイング安値 sl に対し、atrStop が sl の「すぐ内側」なら安値の下へ回す
   条件: atrStop >= sl かつ atrStop − sl < 0.5 × ATR20  →  stop = sl − 0.1 × ATR20
② 深くするのは ATR幅の 1.5 倍まで（安全網）
```

- 🔴 入れた理由＝**ATR×k は値幅しか見ていない**（ユーザー指摘）。誰が見ても支持されている水準の
  すぐ内側に損切りが来ることがあり、そこは真っ先に試される。刈られてから元の方向へ戻られる形がいちばん痛い。
- 🔴 **安値がはるか下にあるときは動かさない**。それは支持を試す位置ではなくただ遠いだけで、
  引きずられると損切りが無意味に深くなる（最初の実装で条件を逆に書いて踏んだ）。
- 🔴 **イベント前は ATR がまだ広がっていない**。FOMC・日銀・米CPI・雇用統計・SQ が2営業日内にある日は
  k を 1.2 倍する（`roboCalendar.eventNear`）。🔵 SQ は `macroCalendar` に無いので `sqCalendar` も見る。
- 🔴 **「その場で決める」に戻してはいけない。** 構造を見るのは事前に決めた純関数の中だけで、
  AI には触らせない。損切りが交渉可能になると、負けている場面ほど「まだ支持線の内側だから」が通る。
  ここが設計原則3の本体で、能力の問題ではない。
- 🔵 **キリ番を避ける案は入れなかった。** 刻みを桁から出すと 200円台の 1571 と 40,000円台の 1321 の
  どちらかで必ず意味を失う。実データが出るまで持たない。
- 🔵 上限（②）は既定値では当たらない（構造で深くなるのは最大 0.6 ATR ぶん・k は 2.0 以上）。
  あとで定数をいじったときに黙って深くならないための安全網として残してある。
- 実データでの効き（2026-08-10 終値・VIX 15.46・CPI前日）＝スイング安値は遠く不発、
  イベント幅だけ効いて k 2.0 → 2.4（例: 1570 は −11.57% → −13.88%）。

### 6.1 トレーリングストップ（2026-08-11 追加・積極化）

```
trail = max(いまの損切り, 終値 − k × ATR20)      k は上と同じ
```

- 🔴 **引き上げるだけ。下げない。** ボラが膨らんだ日に線を下へずらすと「負けを小さく」が崩れる。
- 🔴 **利確ルールは入れない。** 上限を決めて降りると、この戦略でいちばん効く「大きな勝ち」を取り逃す。
- 🔴 **損切り確認の後に引き上げる。** 今日の終値で持ち上げてから今日の終値と比べたら損切りに永遠に触れない。
  今日引き上げた線が効くのは明日から。
- 実装は `trailStop`（純関数）＋ `applyTrail`（口座に書くだけ）。テストで「下げない」を固定してある。
- 入れた理由 ＝ この戦略は**勝率34〜40%が正常**で、期待値は大きな勝ちを取り切れるかでほぼ決まる。
  それまでは損切りが建てた瞬間から動かず、手仕舞いは LLM の毎日の判断任せだったため、
  **早めに利確してしまう余地が構造的に残っていた**（プロンプトで戒めてはいたが仕組みで止めていなかった）。
  プロンプト側にも「利確はシステムが引き受けている」と明記した。
- 🔴 **幅は建値のときの2倍**（`TRAIL_WIDEN`・2026-08-11 夕方に修正）。
  同じ幅で引き上げると26年の検証で **DDそろえ後 −0.93%・売買回数 166→434** と明確に悪化した
  （刈られては入り直すを繰り返す）。2倍にすると −0.02%＝実質ノーコスト。
  🔵 狭いと悪い理由＝**ドンチャン25の安値割れ**という手仕舞いが、すでに価格構造で追いかける
     トレーリングとして働いている。値幅ベースの線を重ねると二重になる（ボラターゲティングと同じ構造）。
  🔴 それでも**外さない**理由＝対照群はルールで降りるが、ロボ口座の手仕舞いは**AIが判断する**。
     AIが降りそこねたときの歯止めがこれで、その価値は対照群の検証には映らない。役目が保険なら幅は広いほうがよい。
- 🔵 DD を増やさない方向の積極化。レバや確信度連動の建玉倍率は**採らない**
  （3倍で CAGR 22%／DD −80%、確信度は本体実測で自信過剰かつ反転）。

## 11.5 🔴 実保有の取り込み（2026-08-09 追加要件）

**ユーザー要件**: 毎回、実際の保有画面のキャプチャを共有するので、それを元にデモ口座を実情に合わせたい。

### 🔴 口座を2つに分ける（この要件を入れるための必須条件）

**ロボ口座を実保有に同期させると、AI の成績が測れなくなる。**
ユーザーが途中で介入した結果（買わなかった／数量を変えた／早く利確した）が混ざり、
「AI の判断が良かったのか、人の介入が良かったのか」が分離できなくなるため。
Go/No-Go（§2 論点2）も対照群比較（§5）も同時に意味を失う。

| ファイル | 中身 | 誰が書くか | 用途 |
|---|---|---|---|
| `robo_account.json` | **AI の独立した疑似口座** | ロボのみ。🔴 **人は介入しない** | 成績の検証（対照群比較・Go/No-Go） |
| `real_position.json` | **実保有**（キャプチャから読み取り） | キャプチャの取り込み処理 | 実情に即した判断・コメント |

### LLM には毎回どちらも渡す

- ロボは**自分の建玉**（`robo_account.json`）で判断する — ここは従来どおり。
- 加えて**ユーザーの実保有**（`real_position.json`）を文脈として読み、
  🔴 **乖離があれば指摘させる**（例:「ロボはベア2倍を保有中だが、ユーザーはブル2倍を保有。逆向き」）。
- 出力スキーマに **`user_note`（ユーザーの実保有に対する所見・1〜2行）** を追加する。
  ロボ自身の売買判断（`action` / `symbol` / `qty`）とは**別の欄**にして、成績集計に混ぜない。

### `public/data/real_position.json`（新規）

```jsonc
{
  "captured_at": "2026-08-09T22:10:00Z",
  "source": "capture",                 // 取り込み経路
  "positions": [
    { "symbol": "1570", "name": "日経レバレッジ", "qty": 30,
      "avg_price": 31200, "last_price": 30850, "pnl": -10500, "pnl_pct": -1.12 }
  ],
  "raw_ocr": { },                      // 読み取り結果の生データ（検算用）
  "confidence": "high",                // 読み取りの確からしさ
  "unreadable_fields": []              // 読めなかった項目（推測で埋めない）
}
```

🔴 **読めなかった項目は推測で埋めない**。`unreadable_fields` に列挙し、
その項目は「不明」として LLM に渡す（数字を作られるのが最悪のケースのため）。

🔴 **実保有の読み取りは Claude の vision で行う**が、これも判断ログ（`robo_logs/`）に
入力画像の参照と読み取り結果を残す。後から「読み取りを間違えていた」を追えるようにするため。

### ✅ TradingView のチャート画像も入れる（2026-08-09 追加決定）

🔵 **「価格が一次情報」と決めたことで、チャート画像の価値が上がった**（§11.6）。
数値では表現しきれない**形**（ダブルトップ、三角持ち合い、ネックライン）を LLM に読ませる。

| | 取得元 | 位置づけ |
|---|---|---|
| 価格の**数値**（終値・MA位置・高安・ATR・トレンド） | Yahoo API | 一次情報の本体 |
| チャートの**形** | TradingView のスクショ | 数値では出せない形の補強 |

**撮影＝ローカル自動化、判断＝クラウド**（2026-08-09 確定）

🔴 **ブラウザ自動化は GitHub Actions では動かない**（無人環境にログイン済みブラウザが無い。
認証情報を Secrets に置くのは2要素認証もあり非現実的かつ危険）。
そこで**撮影だけをローカルに切り出す**:

```
ローカルPC（引け後）: scripts/capture-tradingview.mjs
  Playwright の persistent context（ログイン状態を保持）で TradingView を開く
  → チャートを撮影 → Chatwork の通知ルームへ自動投稿
        ↓（同じルーム）
GitHub Actions: 従来どおり判断・記録・通知。Chatwork から画像を拾う
```

- 🔵 **判断・記録・通知はクラウドのまま**。設計の根幹（Actions で完結）は崩さない。
- 🔴 **撮影が失敗しても判断は止めない**。画像が無ければ**数値だけで判断を続行**する
  （PC が落ちていた日に検証の連続性が切れるのを防ぐ）。
- 🔴 Playwright の `userDataDir`（ログイン状態）は **`.gitignore` に入れる**。コミットしない。
- 初回のみ手動で TradingView にログインする（以降はセッションが保持される）。

### ✅ 受け渡し経路 = **Chatwork**（2026-08-09 確定）

通知と同じルームに保有画面のキャプチャを投稿する。実行時に Actions が取りに行く。

```
ユーザー: スマホの証券アプリで保有画面をキャプチャ → Chatwork の通知ルームに投稿
  ↓
GitHub Actions（引け後）
  1. GET /rooms/{room_id}/files            … 直近のファイル一覧
  2. 最新の画像1件を選ぶ（当日分が無ければ直近のものを使い、何日前かを記録）
  3. GET /rooms/{room_id}/files/{file_id}?create_download_url=1 … ダウンロードURL取得
  4. 画像を取得し、Claude の vision で建玉を読み取る
  5. public/data/real_position.json を更新（captured_at と age_days を必ず入れる）
```

🔵 **通知と同じ場所で完結する**ので新しい経路が増えない。スマホだけで運用できる。
🔵 AutoFBA の SDSチェックAI（Chatworkに画像を投げて処理させる）と同じ運用形態なので、操作に慣れている。
🔴 **ダウンロードURLは短時間で失効する**ので、取得したらその場で処理する（URL を保存しない）。
🔴 **画像そのものはリポジトリにコミットしない**（実口座の残高が git 公開履歴に残るため）。
　 保存するのは読み取り結果（`real_position.json`）と、判断ログ内の読み取り記録だけ。

### ✅ キャプチャが無い日 = **前回分を「古い」と明示して使う**（2026-08-09 確定）

- `real_position.json` に **`age_days`（何営業日前のキャプチャか）** を持たせ、プロンプトにも明記する。
- 🔴 LLM には「**この保有情報は◯営業日前のもので、現在は変わっている可能性がある**」と伝え、
  古い情報を根拠に断定させない。
- 判断自体は止めない（検証の連続性を切らさないため）。
- 🔵 `age_days` が一定を超えたら（例: 5営業日）、通知に「保有画面のキャプチャが古いです」と添える。

## 13. 設計原則との対応（自己点検）

| 原則 | 本設計での担保 |
|---|---|
| 1. リアルマネーはユーザーの手のみ | 証券APIを v1 で使わない。ロボ口座は JSON への記録のみ。**発注経路がそもそも存在しない** |
| 2. 判断はAI、最終判断と責任はユーザー | 🔴 (b) を選んだので疑似口座は自律。リアルはユーザーの判断（本人が明示）。通知に**反証（`counter`）**を必ず載せる |
| 3. 損切りは事前固定・ボラ連動 | `robotStrategy.mjs` の純関数＋テスト。**LLM には決めさせない**。`stop_price` は建玉時に確定し git に残る |
| 4. 検証してから自動化 | 🔴 LLM 判断はバックテスト不可 → **対照群の並走＋Go/No-Go の事前固定**で代替。決定論側は着手前にバックテスト |
| 5. 数値主軸・画像補助 | v1 は数値のみ。画像は v2 以降 |
| 6. 売買推奨ではなく状態記述 | 🔴 **宛先を本人に限定したことで両立**（§10.1）。公開する段では再評価が必要 |
